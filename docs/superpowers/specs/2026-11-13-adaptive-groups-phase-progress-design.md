## 2. 方案选择

分组色采用“按照片生成协调色板 + 组间可辨识约束 + 最终合成校验 + 更明确的组标识”。只提高原六个浅色的固定透明度无法适应不同照片；只用文字保护也会再次把组色洗淡，均不足以完成验收。

用户选择分阶段进度，保留整批导出后统一校验保存。未采用单一时间估算百分比或逐文件提前发布。进度数量是当前阶段的文件计数，不是耗时估算，也不是单文件内部百分比。

## 3. 分组色

### 3.1 四处统一、身份稳定

- 手动文件清单、预检查、运行结果、对应分组输出目录行全部使用整行半透明分组色。不能只修预检查或只画小色标。
- 用规范化完整源目录 Key 作为分组身份，Label 为可见 A/B/AA。禁止用具体 RGB 值作为身份或用组字母简单对六取模。
- 一组在四处消费同一个样式定义。背景图位置不同可产生合成差异，但组色相、强度和组标识一致。
- 目录组列增加较明确的同色小底块/标记，文字 A/B 保留。选择、多选、悬停后仍辨认分组，同时选择/焦点本身也清楚。
- 滚动、筛选、排序、进度更新不重分配颜色。新增组不改变既有组的色相身份。
- 同一照片深浅切换主要改变亮度、彩度和强度，保留各组色相身份。换照片可重新配色。区域缩放/重绘优先保持色板稳定，仅重新验证材料。
- 运行结果保留所属运行的目录身份；当前输入改变后不能把历史 A 组误当新输入中另一个 A 组。样式映射在会话内保存，不把业务路径新增写入 UI 配置。
- 外观预览中的色板及已分配色相也属于可撤销草稿。应用才提交，取消必须恢复原映射；不能只恢复当前位图、下次缩放又使用预览留下的新色相。

### 3.2 颜色选择与保护

深色模式需要能从暗面板上显现的彩色底纹；浅色模式采用有明确颜色感的柔和底纹，不能浅到接近白。照片主色参与整体协调，也检查实际文字背景和照片纹理。

同时检查三类差异：组色相对未分组底层、不同组之间、文字相对最终行材料。不能只比较调色板原始颜色。背景很蓝时仍可含蓝/青，但不能把所有组都分配成近似浅蓝。

设计者选用 Oklab/OKLCH 作为本地候选色与色差计算基础，无需安装依赖；采用 sRGB 相对亮度计算文字对比。颜色算法参考原作者资料：https://bottosson.github.io/posts/oklab/ 。数值是工程筛选，真实视觉验收仍必要。

新增独立“分组颜色强度”0–100，默认65（偏清晰），按皮肤分别保存，和 PanelOpacity 分开。0 可隐藏整行色层但仍保留组字母/标记；1–100 代表期望辨识强度，不直接等于 alpha。自动保护不得改写滑杆保存值。

默认强度下，设计者选定的自动化起点：常见2–6组在确定的合成背景夹具上，组行相对无组行 Oklab 距离至少0.04，组间至少0.05。它们不是通用视觉标准或任意照片的保证；阈值可依据真实验收调整并记录。字体继续最低4.5:1、主要文字优先7:1；组标识和焦点有明确形状/文字辅助。

依次选择合适色相/彩度/明度、必要的色层强度和局部保护材料，联合满足可读性和分组辨识；不得把“不断折半组色直到消失”作为正常路径。强反差图可增强局部保护，但正常图应保持背景可见。多组优先选感知差异较大的候选，不承诺任意多组都能仅凭颜色辨认，依靠字母与标识兜底；禁止六组后机械重复。

状态列保持成功/失败语义和标记，组色不代表执行结果。现有小状态保护底层可以保留并协调配色，不能把整行组色替换成成功绿/失败红。

schema 2 添加可选 GroupColorStrength，旧字段缺失取默认65；兼容 schema 1 的现有迁移，不因此重置旧皮肤。纯色主题保持现有风格与文字保护，可复用更清楚的组标识。

## 4. 分阶段进度的含义

### 4.1 生命周期与分母

准备/初始化：显示“正在准备任务”“正在初始化 NX 环境”，有活动提示但不虚构文件完成比例。冻结计划后公布需要执行的数量。

阶段1“导出”：N 为冻结任务中实际交给 Worker 的条目数，不含预检查已跳过项。跳过数量单独显示，不把旧 PDF 算成本次导出。N 在该阶段固定。

- D 为已经走到真实处理终态并成功写入现有结果快照的条目数，包括生成成功、失败、纯模型、无有效图纸和运行时目标变化等已处理结果。
- G 为其中临时 PDF 已成功生成的条目数；必须等文件关闭和源保护检查完成，不在 builder.Commit 返回的瞬间提前报生成成功。
- 当前条目通过其冻结顺序索引识别，界面显示完整文件名，完整路径可悬停。NX 环境验证通过、文件开始处理后，立即离开初始化文字。
- 真实子步骤包含检查输出条件、打开图纸、检查图纸页、更新视图、生成 PDF、关闭图纸。单文件内部没有接入可靠的数值进度时，仅显示子步骤和已用时间。
- 实际可见示例：“阶段1/2 · 正在导出第11/32个 · 已处理10个（31.25%）· 已生成10个”，下一行显示当前文件和步骤。
- 阶段1的100%只表示此阶段已处理完，等 Worker 退出与最终结果核验期间显示“导出阶段结束，正在核对结果”，不能称整个任务成功。

阶段2“校验并保存”：必须在 Worker 退出且最终 result.json 通过原 WorkerResultValidator 后进入。K 为该可信结果中需要校验发布的临时成功项数，按冻结任务顺序固定；阶段1失败/纯模型/无有效页/预检跳过不重复作为发布工作。

- P 为已尝试校验保存并得到最终结果的数量；S 为真正保存成功数量，包含新增及覆盖；覆盖数是 S 的子集，不重复相加。
- 阶段2的当前索引对应自己的K项列表，再映射回冻结源文件；不能直接复用阶段1的索引，否则前面有跳过/失败时会显示错文件。
- 历史快照变化、临时 PDF 无效、替换失败等计入 P 与保存失败，不能增加 S。
- 显示“阶段2/2 · 正在校验并保存第3/10个 · 已处理2个（20%）· 已保存2个”。
- 切换阶段时明确切换标题/分母并从0计数，不把它呈现为同一个总进度倒退。导出阶段汇总保留可查看。
- K=0 时显示无需校验保存并按真实失败/跳过/取消结果结束，不显示0/0，不编造成功100%。

完成：显示已保存、其中覆盖、失败、跳过/无有效图纸/纯模型、未执行等实际汇总。阶段处理100%不等于成功率100%；最终成功只来自原正式发布流程。

### 4.2 同条双色进度

一个轨道中按当前阶段显示：

- 实色已处理段：D/N，或 P/K。
- 另一色当前处理段：有且仅有一个真实活动条目时占1/N或1/K，紧接已处理段；内部轻微流动/条纹表示正在处理，宽度不模拟该文件的完成程度。
- 余下为尚未处理的中性轨道，不另定义第三个状态色。两项之间/初始化/结束时没有虚构活动文件。
- 示例 N=32、D=10：已处理31.25%，当前条目3.125%，其余65.625%。主百分比仅显示已处理比例，不能把活动条目预先算完成。
- 用整数计数保存进度；显示可格式化到1–2位小数，但未完成时不得舍入成100%。超多文件时当前段很窄，可以附活动指示/文字，不能扩大其占比冒充多完成。

进度配色取同一套照片/深浅模式/实际背景分析，选择可区分的“已处理”“正在处理”和轨道材料。已处理用实色，当前加纹理；图例文字保留。两段是固定进度角色，不跟随当前文件的目录组变色。换皮肤/语言可更新表现，不重置数量、阶段、当前文件或取消状态；动画停止时不能影响精确比例。

## 5. 本地实时反馈与安全边界

采用运行目录中的独立原子快照 progress.json，进度自身 SchemaVersion=1。原 job/result 协议继续为2，Completed 门槛与发布逻辑不降低。进度只供展示，绝不能作为成功、跳过、文件路径、版次或提前发布的依据。

快照字段：SchemaVersion、RunId、单调递增 Sequence、UpdatedUtc、Stage、Total、Processed、Generated、Failed、PureModel、NoValidSheets、其他实际终态计数、CurrentItemIndex（可空，零基）。不重复记录路径，GUI 从本次冻结条目映射名字。可选更新图纸页信息只作子步骤文案，不改总体权重。

Worker 在已读入有效任务后报告初始化，真实 Session/UFSession/安装校验后报告就绪；文件开始/子步骤/结束时写完整累计快照。不存在依赖 GUI 实时读到每条事件的增量计数。两代 Worker 的共享源码同步接入，不并行 NX、不增加 NX API 调用来查询伪百分比。

GUI 启动本次监视器并在 Worker 运行期间读取；设计者选用250ms轮询。每次最多读128KiB，验证 schema/runId/sequence/阶段/索引/分母和计数关系，忽略错误任务、旧序号、非法值，不创建第二条状态路径。不存在文件或读取竞争可重试；有效进度不会回退。

长 NX 调用可以没有新快照；更新时间很久不等于卡死。保留最后确认步骤并显示本地已用时间。连续读取失败才提示“详细进度暂不可用”，不造百分比、不报成功、不强杀进程。尚未收到首次反馈时显示“正在初始化/等待 NX 反馈”；快照无效不切成“正在导出”。观察器故障写诊断，不能改变导出/结果快照的错误处理。

每次运行使用独立 runId/监视器代次。退出 Worker 后停止并收拢导出反馈，再进入 GUI 发布阶段；上一批回调不能覆盖新任务，迟到快照不能把阶段2倒退到阶段1。结束/关窗释放轮询和动画。

发布验证与文件 IO 不得长期占用 UI 线程，否则有数值也看不到刷新。可把单项既有校验/发布放到顺序后台工作并等待，使用冻结数据，UI 状态由同一调度入口应用。不能把逐文件发布改成并行，不能删除原历史快照/目标身份/临时 PDF 校验。避免进度刷新触发全量表格重建或照片重新分析。

## 6. 取消、异常与空任务

- 第一次点击取消立即记录请求，按钮改为已请求并禁用重复点击；若正在准备尚未有 cancel.flag，也要记住请求，不能静默丢失或继续启动新任务。
- 已有原子文件处理不中断。显示“已请求取消，正在完成当前文件并收尾”，实际文件/步骤可继续更新，但不得把取消提示覆盖回普通导出文字。
- 未开始的取消项不加入 D/P，不填充剩余进度到100%。
- 阶段1取消后，按现有规则把已完成的临时 PDF 继续进入阶段2校验保存；保留“取消收尾”提示。不能用同一个取消标志再取消这些本来应该保存的成果。
- 仅在阶段2新提出的取消，完成当前原子发布后不再处理后续项。已保存 PDF 保留，未保存项按既有清理规则处理。
- 全部预检跳过：不启动 NX，显示0个需要导出、跳过数量，直接结束；真正零输入维持现有校验提示。
- Worker 启动失败/崩溃/超时/结果无效时保持实际已有进度，按原错误处理收尾。致命合并器补出的未执行失败项不伪装成已经执行完成。
- 最终权威结果和进度不一致时以既有结果/安全检查决定业务结果，并记录进度异常；不得为了让显示一致而修改正式结果。没有可靠处理计数时保留最后可信值或标未知。
- 不通过计时器自动加百分比，不用 stdout 自由文案解析业务状态，不用临时 PDF 文件大小推算完成度。

## 7. 配色、进度和状态的验收

确定性测试先于实现；照片美观和真实 GUI 仍由用户验收。以实际可运行候选验证：

- 2/6/8组、追加组、排序/筛选、深浅切换、换照片；预检查/运行结果/手动清单/输出四处均有明显整行色。
- 默认分组强度更明确，0/65/100行为可解释；原手动遮罩、字色和照片效果保留；纯色与系统高对比回归。
- 导出阶段与保存阶段各自分母固定，混合成功/失败/无有效图纸/纯模型、预检跳过、零待保存。
- 单个很慢的文件仍显示真实子步骤，当前段不假装推进；当前文件名、数量和百分比同步更新。
- 导出前、导出中、发布中取消；重复取消、迟到消息、两次连续运行、快速切换语言/皮肤。
- 丢/坏/越界/旧runId进度快照、遗漏多次轮询、Worker异常；终态 result.json 是唯一发布依据。
- 两代受支持 NX 各做实际受控多文件验证，观察中间进度快照、最终结果与实际 PDF；每次制图和模型前后哈希，故障/取消使用隔离副本。本轮改了 Worker/观察路径，不能只引用旧 NX 证据声称新进度已实测。
- 100/125/150% DPI、最小窗口和照片复杂区域，双色条及文本不裁切；用户负责 GUI/DPI截图和物理断网，未收证据即待验。

交付新唯一目录中的2.1.0候选、ZIP SHA-256、源码身份和实际测试/构建/双 NX 证据。保留旧包、既有 NX2506 标注视觉差异和人工待验。不推送、不打标签、不创建 Release。任何缺失证据不包装成“全部验收通过”。

## 8. 决定来源

用户决定：整行分组色自适应且包含运行结果、实际执行状态与数量、同条双色进度、自适应进度配色、采用分阶段进度。

设计者补齐：独立组身份、默认强度65与工程色差起点、阶段分母/失败计数、1份活动段、取消优先级/零任务、累计原子快照旁路、轮询/大小限额、迟到与读取失败规则、UI非阻塞和验收矩阵。这些落实已确认目标，无需用户重新选择已确认功能。
